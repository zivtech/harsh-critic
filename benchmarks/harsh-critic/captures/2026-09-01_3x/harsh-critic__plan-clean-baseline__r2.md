**VERDICT: REVISE**

**Overall Assessment**: This is a genuinely thoughtful plan — one of the better rate-limiting proposals I'd expect to see. It names its tradeoffs, rejects alternatives with reasons, quantifies the incident-during-rollout risk with correct arithmetic, and separates attempted from actual traffic. That is real engineering, not fluent furniture. But its polish hides four load-bearing gaps: the anti-abuse control is built for the *shape* of the last four incidents rather than the adversary you create by deploying it; the shadow-mode observation apparatus is 80% unwired (only latency gates enforcement, not false-positive rejection of legit users); the client-facing contract silently contradicts itself under the two-window design; and the single most important safety lever — the immediate-mitigation override — is described in two incompatible mechanisms. None are fatal. All must be fixed before you commit resources.

**Pre-commitment Predictions**: Before reading in detail, I predicted the five classic weak spots for a gateway rate-limiting plan: (1) key-granularity bypass / multi-key minting, (2) fail-open behavior *under the very load it targets*, (3) distributed-counter consistency and added per-request latency, (4) client-header/UX mismatch with multi-window limits and false positives for bursty-but-legit clients, (5) success metrics that are gameable or don't measure end-to-end. **All five materialized.** The plan's fluency masks that it has the standard weak spots — which is exactly the "dead output" risk: a well-written plan that reads as interrogated but wasn't stress-tested on these axes.

**Major Findings** (causes significant rework):

**MAJOR-1 — The per-key control + single-key-share metric are both defeated by multi-key minting, and one of your four named incidents is the deliberate one.**
- Evidence: Step 1 — `"A customer with multiple API keys gets each key limited independently"` and `"the tier value is the same for every key on the account."` Success Metric — `"Peak single-key share of total API capacity: reduced from the observed 40% to under 10%, measured on attempted rate."`
- Why this matters: The Core Thesis claims the approach `"will prevent the abuse pattern we have actually seen"` — and 1 of the 4 incidents (40% of capacity for 6 hours) was *deliberate scraping*. A deliberate abuser confined to one key under the old regime will simply mint keys under the new one. Your own numbers show it: an Enterprise key bursts at 400 rps = 5% of the 8,000-rps peak (implied by Step 6's "2x = 16,000"); **8 keys × 400 rps = 3,200 rps = 40% of peak** — reproducing the exact incident while every key stays under the 10% metric. The Success Metric would report *victory* while the motivating abuse recurs. The plan's scope note defers account-level aggregation to "follow-up," which is a legitimate staging choice — but the Success Metric does not carry that caveat, so it will lie.
- Confidence: HIGH. Realist check: exploit path is an authenticated, non-privileged customer able to create multiple keys (the plan explicitly contemplates multi-key accounts). Requires no special privilege. Holds at MAJOR (not CRITICAL only because 3/4 incidents — accidental loops — are genuinely solved, and key-minting may have unstated friction).
- Fix: (a) Add a per-account attempted-rate metric alongside single-key-share, and state explicitly that the single-key metric does *not* certify account-level protection. (b) Add a per-account API-key cap (or key-minting rate limit) so the tier can't be multiplied trivially — even a crude one closes the deliberate-scraping vector now. (c) Verify how customers mint keys today; if self-serve and unbounded, MAJOR-1 is closer to CRITICAL for the deliberate case.

**MAJOR-2 — Shadow mode captures a baseline but nothing acts on it except latency. The rollout's core value — "learn before you enforce" — is mostly thrown away.**
- Evidence: The *only* hold-gate in the entire plan is latency: Step 6 / Success Metric — `"if the measured cost is higher, we revisit the counter strategy"` and `"If the load test shows added p99 above 15ms, hold at Week 2."` There is **no** defined gate on the shadow-mode *rejection rate*. Step 4's 5%-rejection alert is reactive (fires during Week 3 enforcement, after you've broken clients).
- Why this matters: You built a beautiful dry-run apparatus (Week 1 shadow) whose single most valuable output is "how many *legitimate* requests would we have rejected?" — and you never wire it to a go/no-go decision. Concretely: Free tier is 60/min with a **5 rps burst ceiling**. A single legitimate web page that fires 6+ concurrent XHRs on load trips that ceiling on first paint. Shadow mode would reveal this in Week 1 — but nothing in the plan says "if shadow-mode false-positive rejections for any tier exceed X%, hold and retune the tiers before Week 3." So a mis-tuned tier ships to enforcement, breaks legit users, and violates both the `"good experience for legitimate users"` thesis and the `<10 support tickets` metric — reactively, after the damage.
- Confidence: HIGH. This is the top finding. Realist check: worst case is real customer breakage at Week 3 that shadow mode already predicted and you ignored; detection is fast (Step 4 alerts) but the fix is a rollback + retune cycle *after* customer impact. Holds at MAJOR.
- Fix: Add an explicit Week-2→Week-3 gate: "If shadow/advisory-mode rejection rate for within-limit keys exceeds [threshold] for any tier, hold and retune tier thresholds before enforcing." Validate the Free burst ceiling against real client concurrency during Week 1.

**MAJOR-3 — The latency-causing dependency is introduced in Week 1 but only validated before Week 3; and the shadow counter is a second, hand-rolled implementation whose fidelity to the plugin is asserted, not proven.**
- Evidence: Step 5 Week 1 — shadow mode is `"implemented as a pre-function that runs the same counter logic"`; Step 6 gates the `<15ms` load test to `"Before Week 3."`
- Why this matters: Two problems. (1) **Ordering**: a `pre-function` running "the same counter logic" does a Redis round-trip on the request hot path starting Week 1. So Weeks 1–2 run added Redis latency against *real production traffic* with the latency budget still unvalidated — you find out it's >15ms only at Step 6, after two weeks of customer exposure. (2) **Fidelity**: the `pre-function` is a *separate* implementation of sliding-window math, not the compiled `rate-limiting-advanced` plugin. Every downstream baseline and the entire false-rejection metric (`"replaying shadow-mode counters against enforced decisions"`) assume the two produce identical decisions. Sliding-window weighting of the previous window is exactly the kind of thing two implementations get subtly different. Nothing in Step 6 validates that the shadow counter matches the plugin counter. This is also an internal tension with Step 2, which rejected token bucket partly to avoid `"writing and owning a custom Lua plugin"` — yet Step 5 requires custom Lua counter logic anyway.
- Confidence: MEDIUM-HIGH. Note the pincer: if the shadow read is instead async/sampled (softening the latency point), then the baseline-fidelity point gets *worse* (sampled counter ≠ enforced counter). Either way it's a finding.
- Fix: (a) Move the load test / latency validation to gate Week 1 entry, since Week 1 is the first time Redis is in the per-request path in prod. (b) Add a Step 6 check that the `pre-function` shadow decisions match the `rate-limiting-advanced` plugin decisions on identical traffic before trusting any baseline derived from it.

**MAJOR-4 — The immediate-mitigation override is described in two incompatible mechanisms, and it's the sole lever for the whole time-to-mitigate story.**
- Evidence: Step 4 — operator can `"set a per-key limit directly in the policy file, taking effect within 1 second via the admin API and bypassing the 5-minute billing cache."` Step 2 defines the policy file as `"maps subscription tiers to window parameters"` (per-tier, not per-key) and describes a separate `"deploy path."`
- Why this matters: "Set a per-key limit *in the policy file*" and "taking effect *within 1 second via the admin API*" are two different mechanisms welded into one sentence. If the source of truth is the file (with a deploy pipeline), "within 1 second" is impossible and the 5-minute mitigation SLA is blown. If it's a direct admin-API mutation, then "in the policy file" is wrong and you've introduced config drift from your GitOps source. Two competent operators will implement this differently — and under a live 3am incident, the file-edit interpretation misses the SLA. Compounding: the policy file schema is *per-tier*; a *per-key* override requires per-consumer plugin config the plan assumes exists but doesn't specify. This lever is load-bearing: Step 1 defers immediate throttling to it, Step 4 calls it `"the lever for an active abuse incident,"` and the `time to mitigate < 5 minutes` metric depends entirely on it.
- Confidence: HIGH on the ambiguity; MEDIUM on impact. Realist check: worst case is the mitigation SLA is quietly unmet during the first real incident because ops picks the slow interpretation. Holds at MAJOR.
- Fix: Specify one mechanism precisely: the exact admin-API call, the per-consumer config object it writes, how it takes precedence over the tier mapping, and how it reconciles with the policy file afterward. Then have Step 6's mitigation drill exercise *that* mechanism, cold, with an unprepared on-call operator — not a rehearsed one.

**MAJOR-5 — Response headers expose only the sustained window, so per-second rejections produce a `429` with `RateLimit-Remaining > 0`. This confuses clients, generates the exact support tickets your metric caps, and undercuts the UX thesis.**
- Evidence: Step 3 — `RateLimit-Remaining: requests remaining in the current sustained window`. Step 1 — `"A request is rejected if it exceeds either window"` (per-second OR per-minute).
- Why this matters: A client with 500 requests left on the minute window that trips the 5-rps burst ceiling gets a `429` while the headers say `RateLimit-Remaining: 500`. From the client's side this looks like a broken/flaky API — "you told me I had budget and rejected me anyway." That is precisely what drives confused support tickets (threatening the `<10 tickets` metric) and directly contradicts `"maintaining a good experience for legitimate users."` Compounding: `Retry-After` — when you're rejected by the per-second window it should be ~1s, by the per-minute window up to ~60s; the plan doesn't say which, so clients can't back off correctly. And `RateLimit-Reset` (`"seconds until the sustained window resets"`) is a fixed-window concept — a sliding window has no discrete reset instant, so the value is an approximation that will mislead well-behaved clients.
- Confidence: HIGH. Realist check: no data loss, but it's a systemic mismatch touching *every* rejected request and two stated success criteria. Holds at MAJOR.
- Fix: Expose *both* windows in the rate-limit headers (the RateLimit draft supports multiple policy entries), and set `Retry-After` from the *binding* window (the one that actually rejected the request). Clarify `RateLimit-Reset` semantics for a sliding window in the docs.

**MAJOR-6 — Fail-open is load-correlated: every request (including rejected ones) does a synchronous Redis read, so a volumetric flood can saturate Redis and disable the limiter precisely during the attack. Step 6 tests the binary outage, not this dynamic.**
- Evidence: Step 2 — `"synchronous Redis reads on every request"` and `"fail open... If the Redis cluster is unreachable or times out, the plugin allows the request."` Step 6 failure drill `"makes Redis unreachable"` (binary) at a load test of `"2x current peak (16,000 rps)."`
- Why this matters: Under a scraping/volumetric surge, *every* malicious request — even ones you intend to reject — still costs a Redis round-trip. That means the limiter *amplifies* Redis load in proportion to attack volume. As Redis latency climbs, the per-request timeout fires and the plugin fails open — i.e., the control removes itself at the exact moment it's needed most. The plan explicitly accepts `"abuse is unthrottled during a Redis outage"` as status-quo-equivalent, which is fair for a *random* Redis blip — but it does not address that the outage is *correlated with attack load*, nor that a flood of rejections is itself a plausible cause. Step 6's load test is 2x *legitimate* peak; a real flood is 10–100x, and the failure drill tests Redis fully *unreachable*, not the realistic partial-degradation (high-but-nonzero latency → timeout → fail-open) that actually occurs under attack.
- Confidence: MEDIUM-HIGH. Realist check: worst case = during a volumetric attack the limiter fails open (= no protection, status quo) with `ratelimit_backend_error` firing. Mitigated by: alerting exists, and the floor is "no worse than today's no-limiter state." But the plan's *protection promise* evaporates exactly when invoked. Holds at MAJOR.
- Fix: (a) Specify the Redis timeout and a p99 target under Redis-*degraded* (not just healthy) conditions. (b) Add a Step 6 drill at attack-scale load with *degraded* (high-latency) Redis, not just unreachable Redis. (c) Consider a local fallback counter (even a coarse node-local cap) that engages on fail-open so the limiter degrades to *reduced* protection rather than *zero* protection under attack.

**MAJOR-7 — The counter Redis shares memory with gateway caching, and the eviction policy is unspecified. If it evicts under memory pressure, rate-limit counters silently drop — a limit bypass with no error and no `ratelimit_backend_error` alert.**
- Evidence: Step 2 — Redis is `"separate from application data, already provisioned for gateway caching."` No eviction policy stated.
- Why this matters: This is a *distinct* failure mode from fail-open. If the shared Redis runs a `maxmemory` policy with LRU/random eviction (the common default for a cache), counter keys can be evicted mid-window under cache pressure. An evicted counter resets to zero → the affected key silently regains full budget → the limit leaks. Critically, this emits *no error* — the plugin reads a (missing→zero) counter and allows the request, so `ratelimit_backend_error` never increments and no alert fires. The control fails *invisibly*, which is worse than fail-open (which at least alerts).
- Confidence: MEDIUM (depends on the shared Redis's actual eviction config, which I cannot verify here — this is a plan-gap: it must be specified). Realist check: if the counter keyspace is `noeviction` or on a dedicated instance, this is moot. Because the plan doesn't say, the default footgun is live. Holds at MAJOR pending verification.
- Fix: Put rate-limit counters in a keyspace/instance with `noeviction` (or a dedicated Redis logical DB with its own memory policy), and add monitoring for counter-key eviction/miss rates. State this explicitly in the plan.

**Minor Findings** (suboptimal but functional):

1. **"Roughly 4x" is wrong across the whole table.** Step 1: `"The burst ceiling is set at roughly 4x the per-second average of the sustained limit."` Actual: Free 5x (5 vs 1/s), Basic 3x, Pro 2x, Enterprise 1.6x. The multiplier isn't ~4x — it decreases monotonically, meaning **burst protection is weakest exactly where a single key can do the most absolute damage** (Enterprise: 400 rps sustainable for ~37s before the minute window binds). The tiers may be deliberate, but the stated derivation rule is false and the shrinking-ratio implication went unnoticed.

2. **"Baseline for all four" — there are five Success Metrics, and the baseline sourcing is inconsistent.** The Goal says each metric is `"measurable against a baseline we capture in Step 5 shadow mode"` and Success Metrics says `"Baseline for all four is captured during Week 1 shadow mode."` Five metrics exist. And at least three don't get their baseline from shadow mode: latency is validated in Step 6, single-key-share baselines off the *historical* 40%, time-to-mitigate off the Step 6 drill. Only the false-rejection metric genuinely uses shadow counters. One-line edits fix it, but it signals the metrics section wasn't reconciled with the phases.

3. **False-rejection metric has a questionable denominator and a confused measurement mechanism.** `"<0.05% of all 429s"` couples the quality metric to abuse volume (a better denominator is false-429s / requests-from-within-limit-keys). And `"replaying shadow-mode counters against enforced decisions"` compares Week-1 data to Week-3 data — different request streams; you can't replay one week's counters against another's decisions. The intended mechanism (a parallel shadow oracle running *during* Week 3) is never stated.

4. **Advisory signal is only one week of machine-readable warning.** Week 1 is silent shadow (no header); the `RateLimit-Warning` header appears only in Week 2; Week 3 enforces. Consumers get exactly one week of concrete signal to detect, add retry logic, and deploy. For B2B/enterprise consumers with change-management cycles, that's thin — the 2-week email helps but isn't a technical signal. Also, `RateLimit-Warning` is a nonstandard/invented header (the HTTP `Warning` header is deprecated) and collides conceptually with the standard `RateLimit-*` fields from Step 3.

5. **`Retry-After` jitter direction unspecified.** `"up to 20% random jitter"` — additive-only is safe; if it can subtract, clients retry before the window clears and eat a wasted rejection. State that jitter is additive.

6. **Rollback is all-or-nothing.** The only rollback is `"disable the rate-limiting plugin"` — the whole control. A single mis-typed tier in the policy file (Enterprise `1,500` instead of `15,000`) throttles your biggest customers, and the only remedy is disabling limiting entirely. No policy-file validation/CI, staging, or canary of config changes is mentioned.

**What's Missing** (gaps, unhandled edge cases, unstated assumptions):

- **No per-account key cap or key-minting limit** — the enabling condition for MAJOR-1. (Gap)
- **No shadow-mode rejection-rate gate** — the enabling condition for MAJOR-2. (Gap)
- **No audit of first-party consumers of the *public* API.** The plan assumes internal traffic all `"bypasses the gateway entirely."` If any first-party surface (mobile backend, first-party web app) calls the public API *with an API key*, it gets tiered and can be throttled. No inventory of who's on the keyed path.
- **"Enterprise / Custom SLA customers" collapsed into a single 15,000/min bucket.** The tier is literally labeled `"Custom SLA customers"` yet given one fixed number. If any Enterprise contract promised higher/unmetered throughput, this uniform cap *breaches the contract*. The only per-customer lever described is the abuse *override* (a throttle), not a standing legitimate *raise*. (MEDIUM confidence, product/contract risk.)
- **Redis memory/write-throughput headroom for counters is assumed, not sized.** "Already provisioned for gateway caching" ≠ provisioned for per-request sliding-window counter churn at 16,000 rps. Plus the eviction gap (MAJOR-7).
- **Human availability for the override is unmodeled.** The `<5 min` mitigation SLA implicitly assumes an on-call operator responds and executes within budget. The Step 6 drill uses a prepared operator, which doesn't represent a 3am cold response.
- **No end-to-end abuse-to-mitigation metric.** Time-to-mitigate is defined `"from alert firing"` — excluding the up-to-15-minute detection latency baked into Step 4's `"5%... over a 15-minute window"` alert. Real abuse-to-mitigation could be 20+ minutes while the metric reports `<5`. (Vanity-metric smell; still a big improvement over 6 hours, but the framing understates true time.)
- **Concurrency limiting was never considered.** The decision was framed as "which windowing algorithm" (fixed vs sliding vs token bucket) — all rate-based. For the *accidental infinite loop* case (3 of 4 incidents), a per-key **max-in-flight-concurrency** cap is often simpler, catches runaway loops directly, and adds no per-request Redis dependency. Its absence is a false-dichotomy within the rate-limiting family.
